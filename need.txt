## 10. FIRESTORE SECURITY RULES

The project previously used restrictive rules that denied all reads and writes:

```
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {
    match /{document=**} {
      allow read, write: if false;
    }
  }
}
```

The rules were later changed to allow the authenticated user to read their own admin document.

Create a complete, secure ruleset based on the actual collections and field structure.

The rules must:

* Allow public read access only to intended public portfolio content.
* Deny public writes to portfolio data.
* Allow only the authorized owner to create, update, or delete portfolio records.
* Validate the owner's authenticated UID and admin role.
* Restrict access to the `admins` collection.
* Prevent public users from changing their own roles or granting themselves owner access.
* Avoid allowing unauthenticated writes.
* Protect any private fields or administrative data.
* Account for Firestore's security-rule evaluation behavior when a rule reads an admin document.

Do not use `allow read, write: if true` as a permanent solution.

If collection-level public read access is too broad, suggest a dedicated public-content model or separate public and private documents.

Explain how to publish and test the rules in Firebase Console.
